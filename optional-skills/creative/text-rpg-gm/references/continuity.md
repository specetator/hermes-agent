# 连续性与恢复

## 文件分工

| 文件 | 用途 |
| --- | --- |
| `trpg_save.md` | 唯一正式主存档：已确认设定、事件摘要、当前有效断点 |
| `checkpoint.json` | 当前分支的近期状态、来源、待决选择、撤回项 |
| `relationships.md` | 当前关系阶段、已发生的关系里程碑及来源 |
| `characters/<id>.md` | 稳定身份、当前动机、资源、认知边界和表达习惯 |
| `archive/` | 更新前备份；仅作历史证据，不作为默认续跑入口 |

通用 profile 记忆只放工作偏好与项目入口。角色数据库留在对应作品中。

## 恢复决策

1. 核对用户要求的作品与资料路径。提及、比较或否定另一部作品不触发切换。
2. 读最新用户指令，再读检查点、主存档和关系索引。按明确来源确定哪些事件有效。
3. 若旧档落后，查近期原文；用户已否定的助手段落不可恢复为事实。
4. 检查点缺少来源或关系发生冲突时，查具体历史。不能用流畅续写掩盖证据缺失。
5. 用一条有效断点继续，不重演已经结束的到达、交谈或离场。

## 检查点字段

公开 JSON 模板用于文件模式；它不是自动插件的严格 API schema。插件适配时应按实际接口映射。

| 字段 | 含义 |
| --- | --- |
| `project_id` / `branch_id` | 作品与当前分支，防止把两条剧情合成一条 |
| `revision` | 本地版本序号，每次有效更新递增 |
| `source` | 用户确认、修正或有效原文出处；不能只写“来自记忆” |
| `story_time` / `location` | 作品内时间与当前地点，不使用现实文件修改日期替代 |
| `present` / `absent` | 在场与离场人物，二者不交叉 |
| `physical_state` | 重要物品位置、开封状态、受伤或其他当前物理状态 |
| `viewpoint` / `action_owner` | 叙述视角与下一步关键行动权 |
| `knowledge_boundaries` | 角色已知、未知与信息渠道 |
| `last_confirmed_action` | 最新有效动作，避免把计划写成完成 |
| `pending_player_decisions` | 待玩家选择事项 |
| `author_notes` | 已收到的作者指导，未发生事项仍是计划 |
| `retracted_facts` | 已作废事项与纠正依据；历史检索不能使其复活 |

## 写入约定

单写入者读取当前版本后修改，写前再读确认；发现变化先合并，不能覆盖。正式存档先备份再更新，回读核对事实。多会话各用独立分支目录或检查点文件；共享主存档只在明确合并时更新。

这些是文件工作流约定，不能提供原子事务保证。自动插件应使用带预期版本的事务写入、会话身份校验与分支隔离。

## 从纠错提炼规则

用户纠正“角色不知道信封内容”时，分别处理：

- 事实修复：信封仍未拆；将已读内容列为撤回。
- 角色修复：人物卡保留其真正已知的信息，不让错误残留为稳定背景。
- 流程修复：以后写消息或远程对白时检查信息通道。
- 风格修复：只有用户明确提出的文风偏好进入该作品风格记录。

把错误归因到可检查机制，不为每次失误堆一条含人名的全局禁令。
